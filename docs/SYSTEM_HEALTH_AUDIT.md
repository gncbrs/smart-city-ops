# Smart City Operations Center — System Health Audit

Date: 2026-08-30
Scope: full read-only audit of `frontend/src` and `Src/`, verifying claims in `CLAUDE.md` against actual source, and hunting for gaps not yet covered by prior phases.

## Executive Summary

**Overall health: 7.5 / 10.** The codebase is in genuinely good shape for a solo-iterated project — Clean Architecture layering is real and enforced (no EF/Infrastructure leakage into Domain/Application), the DB-level concurrency guard for task assignment is real and correctly implemented, the SSOT migrations for statistics/timeline/movement-history/priority-score/field-unit-status-lifecycle are all verified true in code. However, this audit found one genuine correctness bug that contradicts a documented SSOT claim, one unhandled-exception gap that can 500 a valid request, one silent-crash risk in the incident generator, and several consistency/performance gaps that accumulated as features were added without a follow-up pass.

**Top 3 critical priorities:**
1. ✅ **RESOLVED in Phase 5.35 (`docs/DEVELOPMENT_LOG.md` Part 12 §60).** ~~`IncidentService.GetAllAsync`'s `IsReadyToResolve` computation is wrong~~ (`Src/SmartCityOps.Infrastructure/Incidents/IncidentService.cs:30`) — it treated `Reassigned`/`Cancelled` tasks as "still active" forever, permanently blocking a legitimate incident from ever showing as ready-to-resolve once any task on it was ever reassigned or cancelled. The replay service (`OperationsReplayService.IsTaskActiveAt`) already had the *correct* logic sitting right next to it in the same codebase — this was a live-vs-replay behavioral divergence. Fixed by changing the filter to `.Where(t => t.Status == OperationalTaskStatus.Assigned)`, matching `IsTaskActiveAt`'s terminal-state treatment.
2. ✅ **RESOLVED in Phase 5.35 (`docs/DEVELOPMENT_LOG.md` Part 12 §60).** ~~`FieldUnitService.UpdateStatusAsync` can throw an unmapped `ArgumentException`~~ (`Src/SmartCityOps.Infrastructure/FieldUnits/FieldUnitService.cs:75`) that `DomainExceptionHandler` had no case for, surfacing as a raw 500 instead of 400 for a garden-variety invalid-status-string request. Fixed by adding `ArgumentException => StatusCodes.Status400BadRequest` to `DomainExceptionHandler`'s switch and removing the redundant local try/catch in `IncidentsController.Create`.
3. ✅ **RESOLVED in Phase 5.35 (`docs/DEVELOPMENT_LOG.md` Part 12 §60).** ~~Incident Generator's POST loop only catches `HttpRequestException`~~ (`Src/incident-generator/Worker.cs:58-70`) — a timeout (`TaskCanceledException`), a JSON error, or any other exception from `PostAsJsonAsync` was uncaught and would silently terminate the `BackgroundService` for the rest of the process's life, contradicting the "can't crash/die silently" requirement. Fixed by broadening the catch to a general `Exception` (logged as a warning, loop continues) with a dedicated no-op branch for a genuine shutdown-triggered `OperationCanceledException`.

## Backend & DB Findings

### Critical
- ✅ **RESOLVED in Phase 5.35 (`docs/DEVELOPMENT_LOG.md` Part 12 §60).** ~~`IsReadyToResolve` is computed incorrectly for live data.~~ `Src/SmartCityOps.Infrastructure/Incidents/IncidentService.cs:30` built `incidentIdsWithActiveTasks` via `.Where(t => t.Status != OperationalTaskStatus.Completed)`. `OperationalTaskStatus` (`Src/SmartCityOps.Domain/Enums/OperationalTaskStatus.cs`) has four values: `Assigned`, `Completed`, `Reassigned`, `Cancelled`. This filter counted `Reassigned` and `Cancelled` tasks as "active" — but those are **terminal** states that should never block readiness once past their own `ReassignedAt`/`CancelledAt` timestamp. Concretely: cancelling a task via `POST /api/operational-tasks/{id}/cancel` (`OperationalTaskService.CancelAsync`, `OperationalTaskService.cs:213-241`) would leave that incident's `IsReadyToResolve` `false` **forever** in the live view, even if a brand-new task was later assigned and fully `Completed` — because the old `Cancelled` row for that incident still satisfied `Status != Completed`. Same for `Reassigned`.
  `Src/SmartCityOps.Infrastructure/OperationsReplay/OperationsReplayService.cs:173-183`'s `IsTaskActiveAt` already handled this correctly — a `Reassigned` task is only "active" up to its `ReassignedAt`, a `Cancelled` task only up to its `CancelledAt`. **Fix applied**: the live-path filter now reads `.Where(t => t.Status == OperationalTaskStatus.Assigned)`, matching `IsTaskActiveAt`'s terminal-state semantics; `CreateAsync`/`ResolveAsync` were verified already consistent and needed no change.

### Moderate
- ✅ **RESOLVED in Phase 5.35 (`docs/DEVELOPMENT_LOG.md` Part 12 §60).** ~~`FieldUnitService.UpdateStatusAsync` throws a raw, unmapped `ArgumentException`.~~ `Src/SmartCityOps.Infrastructure/FieldUnits/FieldUnitService.cs:75` (`if (!Enum.TryParse<FieldUnitStatus>(...)) throw new ArgumentException(...)`). `Src/SmartCityOps.Api/ExceptionHandling/DomainExceptionHandler.cs:14-20`'s switch only mapped `KeyNotFoundException`→404, `ValidationException`→400, `ResourceConflictException`→409, `InvalidOperationException`→409 — there was no `ArgumentException` case, so it fell through the `_ => 0` default and `TryHandleAsync` returned `false`, meaning ASP.NET's default unhandled-exception pipeline took over (raw 500, not a clean 400). `Src/SmartCityOps.Api/Controllers/IncidentsController.cs:29-37` had manually wrapped its one `ArgumentException`-throwing call site in a local `try/catch` — an inconsistent, one-off patch rather than a systemic fix, and it leaked a Turkish-language error string (`"Yanlış veya eksik argüman."`) into an otherwise English error-handling contract. **Fix applied**: `ArgumentException => StatusCodes.Status400BadRequest` added centrally to `DomainExceptionHandler`, and the redundant local try/catch in `IncidentsController.Create` was removed.
- **`DomainExceptionHandler`'s blanket `InvalidOperationException => 409` mapping is overly broad.** `Src/SmartCityOps.Api/ExceptionHandling/DomainExceptionHandler.cs:16`. `InvalidOperationException` is a very common BCL exception (thrown by, e.g., LINQ `Single()`/`First()` on empty sequences, disposed-object access, etc.) — any *accidental* bug that happens to throw this exact type anywhere in a request's call path will be silently reported to the client as a clean "409 Conflict" business-rule violation instead of surfacing as a 500 that would get noticed/logged as a real bug. It currently works because the only deliberate throw sites are the two guard clauses in `FieldUnitService.UpdateStatusAsync:79,84` and `IncidentService.ResolveAsync:70`, all of which are genuine conflicts — but this is a fragile coupling between exception *type* and HTTP *semantics* rather than an intentional, named domain exception. Low urgency, but worth a defensive follow-up (e.g. introducing a dedicated `DomainConflictException` and reserving `InvalidOperationException` for genuine bugs) before the codebase grows further.
- **`IncidentService.ResolveAsync` does not enforce the `IsReadyToResolve` invariant server-side.** `Src/SmartCityOps.Infrastructure/Incidents/IncidentService.cs:60-99` — `POST /api/incidents/{id}/resolve` only guards against double-resolving (`if (incident.Status == IncidentStatus.Resolved) throw ...`); it does not check whether the incident actually has zero active tasks before force-completing all `Assigned` tasks and marking it `Resolved`. The `IsReadyToResolve` DTO field is therefore purely advisory UI guidance (the frontend only *filters* the "Ready to Resolve" table on it, per `ActiveTasksPanel.tsx`) with no server-side enforcement — any client (or a stale UI, or a direct API call) can resolve an incident with in-flight units still on the way. This may be an intentional "operator override" design choice, but it is not documented as such anywhere, and is worth an explicit decision one way or the other.
- **`FieldUnitService.GetMovementHistoryAsync`'s query-syntax LINQ projects `inc.Type.ToString()` inside an `IQueryable` before materialization** (`Src/SmartCityOps.Infrastructure/FieldUnits/FieldUnitService.cs:44-58`, specifically `inc != null ? inc.Type.ToString() : null` inside the `select` of a query executed via `.ToListAsync()`). This is the same *category* of pattern (calling a C# method on an enum inside an EF Core query prior to materialization) that caused the confirmed, already-fixed bug in `OperationalStatisticsService` (Phase 5.27's `g.Key.ToString()` inside a `GroupBy(...).Select(...)`). Direct `.ToString()` on a non-grouping enum column is more often translatable by modern EF Core/Npgsql than the `GroupBy` case that broke before, so this may well work — but it was not possible to confirm via static reading alone, and it is exactly the failure mode the team has already been burned by once. Recommend either a manual smoke test of `GET /api/field-units/{id}/movement-history` against a real incident-linked history row, or defensively materializing the join first (`.ToListAsync()`) and projecting the `.ToString()` afterward, matching the pattern `OperationalStatisticsService.cs:47-53` already establishes as the house style.
- **REST surface has no single-resource `GET /{id}` endpoints anywhere.** Confirmed by exhaustively grepping every controller's `[HttpGet]` attributes (`Src/SmartCityOps.Api/Controllers/*.cs`): `IncidentsController`, `FieldUnitsController`, `OperationalTasksController`, `RestrictedZonesController`, `OperationalZonesController`, `FieldUnitLocationHistoriesController` all expose only a list-returning `GET` (plus feature-specific sub-routes like `/{id}/timeline`), never a plain `GET /{id}`. This isn't necessarily a defect — the frontend never needs it, since it always has the full list in a React Query cache and derives single entities via `operationsSelectors.ts` — but it is a real gap against conventional REST resource design, and it means there is no way to fetch a single incident/field-unit/task directly (e.g. from an external client, a deep link, or a future notification system) without pulling the entire collection.

### Low / Cosmetic
- `IncidentsController.Create` (`Src/SmartCityOps.Api/Controllers/IncidentsController.cs:29-37`) mixes a Turkish error string into an otherwise English codebase/error contract (every other user-facing exception message in `Src/SmartCityOps.Infrastructure` is also Turkish, e.g. `"Incident bulunamadı."`, `"Task bulunamadı."` — this is consistent *within* the backend's exception messages, so this is a very minor nit, not a real inconsistency once you look at the whole codebase; noting only because CLAUDE.md documents the codebase's convention as otherwise English for structural comments).
- Controllers are otherwise appropriately thin — every controller method is a 1-3 line inject-call-return, with zero business logic observed in any of the 8 controllers reviewed.
- `Incident-generator`'s `Worker.cs` correctly sources zone data exclusively from `AnkaraOperationalZones.All` (`Src/incident-generator/Worker.cs:80-93`) via its `SmartCityOps.Domain` project reference — no duplicated zone table found, confirming the Phase 5.13 unification claim.

### Concurrency / Atomicity — verified correct
- The DB-level concurrency guard is real: `Src/SmartCityOps.Infrastructure/Persistence/Configurations/OperationalTaskConfiguration.cs:23-25` defines a partial unique index on `FieldUnitId` filtered to `Status = 'Assigned'`, and `OperationalTaskService.AssignFieldUnitAsync` (`OperationalTaskService.cs:180-205`) catches the resulting `PostgresErrorCodes.UniqueViolation` and rethrows it as a clean `ResourceConflictException` → 409. This correctly closes the "read rule pipeline as Available, then both requests try to dispatch the same unit" race, because the entire assignment (field-unit mutation + task insert) happens inside one `SaveChangesAsync` call, so a unique-constraint violation rolls back the field-unit status change too — verified by manual trace, not just by reading the try/catch.
- `AssignFieldUnitAsync`, `CreateAsync`, `ReassignAsync`, and `CancelAsync` were each traced end-to-end: `AssignedAt`/`CompletedAt`/`ReassignedAt`/`CancelledAt` and field-unit coordinates/status are set consistently on every path, and the "reassign old task" / "cancel task" / "complete task" transitions all correctly flip the associated field unit back to `Available` in the same transaction. No read-then-write gap was found beyond the one already closed by the unique index above.
